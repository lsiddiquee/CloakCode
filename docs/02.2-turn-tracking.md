## Remote session list + liveness classification (§3.3)

Enumerating `transcripts/*.jsonl` across all workspaces yields a working session picker
(11 sessions found). Per session: `sessionId`, workspace, title (first `user.message`),
turn count, status, age.

> **Status must use liveness (file mtime), not the last event type** — transcripts often
> end on `assistant.turn_start`, which naively looks "running" even for weeks-dormant
> sessions. `live = mtime < 120s`; `blocked = live + open interactive tool`; else `idle`.

Reproduced by [`research/list_sessions.py`](../research/list_sessions.py) and
[`research/inspect_session.py`](../research/inspect_session.py).

## Observer liveness ceiling — message-granular, not token-live (§3.6)

From `sessionTranscriptService.ts`: transcript entries are **buffered in memory** and written
only on **`flush()`**, which fires at **discrete points** (turn boundaries, tool start/complete,
and before every hook) — **not** continuously. `assistant.message` is a **single entry with the
full `content`** (no partial/streaming entry). The `debug-logs/main.jsonl` copy has its own
timer (`github.copilot.chat.agentDebugLog.fileLogging.flushIntervalMs`, default 4000 ms; see
[02.4 §4.25](02.4-storage-and-logs.md)).

**Consequence:** a file observer **cannot token-stream**; its ceiling is **message-granular** —
user message appears → (silence while the assistant generates) → the whole assistant message
appears on flush → tool cards update on start/complete. To feel more live without owning the
loop: the hybrid `fs.watch` + short mtime-poll follower catches flushes sub-second, and a no-op
flush-forcing hook makes tool cards real-time. **Token-live** requires owning the `vscode.lm`
loop (opt-in "live chat", docs/05).

## Mid-turn (in-flight) tracking, and why steer/queue/stop leave no on-disk marker (§4.28)

To offer the three panel actions (steer / queue / stop-and-send) the observer must know whether a
session is **mid-turn** — the model is generating. Signal: an open `assistant.turn_start` with **no
matching `assistant.turn_end`** at EOF, mirroring the blocker signature but for the whole turn. Two
guards against false positives (both live-validated in the scanner):

1. **Self-heal** — a new `assistant.turn_start` **resets** the prior open turn, because
   **editor-hosted** sessions omit `turn_end` ([02.4 §4.10](02.4-storage-and-logs.md)/§3.3) and a
   dangling start would otherwise read "mid-turn" forever; the reset is on `turn_start` **only**,
   not `user.message`, since a **steer is recorded as an ordinary mid-turn `user.message`** (§3.1)
   and must not clear the in-flight turn.
2. **Live-gate** — like `blocked`, mid-turn counts only while the transcript is live by mtime, so a
   dormant `turn_start`-ended transcript reads idle.
3. **Placeholder guard (fix 2026-07-15, real bug):** Copilot writes a **spurious
   `assistant.turn_start` immediately after every `assistant.turn_end`** — SAME timestamp,
   `parentId` = that turn_end — as a pre-allocated "next turn" that **never runs** (verified: 3290
   starts vs 3281 ends in one live log; the transcript idles ending on this **childless** start). A
   naive "open turn_start = mid-turn" therefore sticks `inTurn` **true forever** on an idle session
   (the exact §3.3 trap that forced _status_ off the last event). Disambiguator: a turn that opened
   **right after a `turn_end`** and has since seen **no assistant activity** (`assistant.message` /
   `tool.*` / `function`) is the placeholder → **not** mid-turn; a real turn either follows a
   `user.message` or gains a child event as the model works (an auto-chained turn after a `turn_end`
   is caught by the activity check).

Surfaced as `SessionSummary.inTurn` (docs/03). **Crucially, the action TYPE is not observable:** a
steered message lands in the transcript as a **plain `user.message`** (normal `parentId`, no
steer/queue tag) and a stopped/force-stopped turn ends with an ordinary `assistant.turn_end` (no
`reason`/`aborted`/`cancelled` field) — both LIVE-CONFIRMED 2026-07-15 via `steerWithMessage` /
`chat.cancel`. So CloakCode tracks only **in-flight-ness**, never labels a message as
steer/queue/stop — matching Copilot's own persisted history, which shows no such marker either (the
"Steering" divider and stop button are transient/live-only). The command mechanics (which
`workbench.action.chat.*` drives each action) are wired and tabulated in docs/03 "Mid-turn flag"
(SHIPPED 2026-07-15). **Force-stop nuance:** a force-stop **mid-tool** orphans a
`tool.execution_start` (blocker-shaped) but is followed by `assistant.turn_end`; the existing "a new
turn supersedes an open interactive tool" rule already prevents a phantom blocker (see
[02.3 §4.19](02.3-tool-call-handling.md)).

**Live-streamed (SHIPPED 2026-07-16):** `inTurn` now also streams over `session.subscribe`
(`{kind:"turn", inTurn}`) so the composer flips steer/queue↔send on transition, not only on a
`sessions.list` refresh (docs/03 "Mid-turn flag"). _Source correction (§4.34, 2026-07-24):_ the
stream is now driven by the **debug-log's** turn spans (`computeInTurnFromDebugLog`), not the
transcript's `computeInTurn` — the transcript proved an unreliable turn source.

## `inTurn` is debug-log-authoritative — the transcript is an unreliable turn source (§4.34)

**Convergence fix (2026-07-24).** `inTurn` had drifted into **four parallel state derivations from
three sources** — the transcript's `computeInTurn`, the scan's mtime `status`, and the client's
"tool calling" — that disagreed. Root cause on the turn source: the **transcript is unreliable for
turn boundaries.** It appends a spurious placeholder `assistant.turn_start` after **every**
`turn_end` (same timestamp, §4.28) and can strand **orphaned tool echoes**, so even with the §4.28
placeholder guard it read "mid-turn" for **~8 of 9** real sessions — only the mtime `live` gate
rescued the idle ones, and the genuinely-**active** session read `inTurn: true` **persistently** (the
composer stuck on **Steer**). This disproves the earlier assumption that turn boundaries can be read
reliably from the transcript.

**The debug-log has clean spans.** `debug-logs/<id>/main.jsonl` carries unambiguous
`turn_start`/`turn_end` boundaries (verified across **all 10** workspace sessions: idle sessions end
on `turn_end`; only a genuinely-live one ends on `turn_start`). Fix: a new
**`computeInTurnFromDebugLog(content)`** (last turn-boundary span wins) now drives `inTurn` in **both**

1. the **follower** (`SessionFollower`, via an injected `computeTurn` reading the **same** tailed
   file), and
2. the **scanner** (`scanSessions`, a debug-log read for `live` sessions only),

while the transcript parser (`computeInTurn`) stays the **no-debug-log fallback**. The separate
`turnFile`/`turnWatcher` plumbing in `SessionFollower` was **deleted** — turn state now comes from
the **one** authoritative tailed source. This matches the existing event-stream design, where
`findSessionLog` already prefers the debug-log and the transcript only backfills the opening
([02.4 §4.10](02.4-storage-and-logs.md)/§4.23).

**Client activity converged on the same flag** (docs/03 "Derived session activity"). `sessionActivity`
shows **"tool calling"** only while `inTurn` **with** a `running` tool part, and **"working"** while
`inTurn` with **no** running part (debug-log tools are recorded `done`, never `running`); the header's
active/idle **age** comes from a live `lastActivityAt` (bumped on each turn transition), not the frozen
session-summary snapshot, so a just-ended turn reads **active**, not a stale "idle 16m".

**PARKED (minor):** a pure **Stop** (`chat.cancel`) writes **no** debug-log `turn_end`, so the
follower's `inTurn` stays stuck `true` after a Stop until the next real turn. A client-side
**optimistic** reset (`ChatComposer` `onStopped` → dispatch `inTurn:false` on the stop-ack) masks it
in the UI; the proper root fix (the observer detecting the cancellation itself) is **deferred**
(docs/05 Known issues).
